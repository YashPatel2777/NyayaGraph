# Legal GraphRAG Platform: documentation index

Version 1.2 (proposed) | 20 November 2026

This folder is the complete specification for the backend. It is written so a coding agent (Antigravity) or a developer can build the system phase by phase without further explanation.

## Using this project in Antigravity

1. Open the `legal-graphrag/` folder as the workspace.
2. `AGENTS.md` in the workspace root is read as an always-active rule. Per Antigravity's rules page, `AGENTS.md`, `GEMINI.md` and an `.agents/rules/` folder are all valid workspace rule locations. One third-party guide says `AGENTS.md` support arrived in IDE version 1.20.5; if your IDE ignores it, rename `AGENTS.md` to `GEMINI.md`. Keep only one of the two, because the precedence when both exist is not documented.
3. `.agents/rules/*.md` hold two glob-triggered rules (data access safety, statute parsing). Antigravity also accepts the older `.agent/rules/` folder name.
4. Start the agent with a prompt like this:

> Read AGENTS.md, then docs/00-overview.md, docs/06-file-structure.md and docs/05-roadmap.md. Implement Phase 0 only. Before writing code, list the spec sections you will implement and the files you will create. When done, run the Phase 0 exit check and show the output.

Repeat for Phase 1, 2 and so on. Do not ask for several phases at once; each phase has its own exit criteria.

## Proposed spec changes for Phase 2

**Decisions (2026-11-20):** SC-5 and SC-6 approved and applied to 02 (2.1, 2.3, 2.4), 03 (3.4), 04 (4.3, P-13 to P-18) and 05 (G10, G11). **SC-5 (approved). Parsing path for rules documents (`kind` rule or regulation).** P-01, P-05, P-06, P-07, P-09, P-10, P-11 and P-12 apply as written, except where the rules below replace them. Rules are stored with the Act model unchanged: the document is an `Act` node with `kind: 'rule'`, each rule is a `Section` (`sec:{act_slug}:{rule number}`), each sub-rule is a `Clause` of kind `subsection`.

- P-13 Body start (replaces P-02 for rules). Discard everything before the first line that P-06 accepts as a heading numbered 1. Text in other scripts and the Gazette header before it are discarded with it. In the Jurisdiction Rules file this drops the Hindi version of rules 3 to 5: its lines start `3.` but fail P-06's `[A-Z]` title test.
- P-14 Enabling text (replaces P-03 for rules). The paragraph starting `In exercise of the powers conferred by` up to rule 1 is stored in a new property `Act.enabling_text`. It is never a LegalUnit and never embedded. Rules have no Statement of Objects, and its absence is not an error.
- P-15 No chapters. A rules document without `CHAPTER` headings gets no Chapter nodes, and its Sections hang directly off the Act through `HAS_SECTION` (2.4 currently says Chapter to Section; extend it to Act or Chapter to Section). `chapter_number` is null.
- P-16 Definitions in rules. In the rule titled `Definitions`, a line matching `^[(][a-z]{1,3}[)][ ]+[“"]` starts a definition Clause labelled with the letter(s), e.g. `cl:cp-jurisdiction-rules-2021:2:a`. This needs the 2.1 clause-label grammar extended to lowercase letters for rules. No LegalConcept nodes are created from rules: concept ids are global (`con:{term}`), so a rule defining `Act`, `seller`, `platform` or `user` would overwrite or flood R-13's whole-word definition matching. Rule definitions are still embedded and searchable as units.
- P-17 References inside rules (extends P-10). In a rules document, `section N` and `section N of the Act` refer to the parent Act given in `issued_under` (REFERS_TO `sec:{parent}:N`, a cross-document edge; a missing target is a warning). `clause (N) of section 2 of the Act` links to `cl:{parent}:2:N`. `rule N` and `sub-rule (N)` refer to this document. The other-Act test of P-10 still applies, so `section 79 of the Information Technology Act, 2000` creates REFERS_TO_ACT to `act:information-technology-act-2000` and no REFERS_TO.
- P-18 Amendments by notification (extends P-09). A footnote such as `Subs. by G.S.R. 328(E), dated 17-5-2021 (w.e.f. 17-5-2021)` is recorded in `Section.amendment_notes`. It creates no AMENDS edge, because a notification has no Act number to form a stub Act id. The `Prior to substitution it read as:` text is part of the footnote and is removed from the body.
- Acceptance tests (new, in `tests/golden/`). **G10:** the Jurisdiction Rules give exactly 5 Section nodes, PRESCRIBES_FOR edges 3→`sec:cpa-2019:34`, 4→`sec:cpa-2019:47` and 5→`sec:cpa-2019:58`, no Devanagari character in any node text, and rule 3's text contains `fifty lakh rupees`. **G11:** the E-Commerce Rules give exactly 8 Section nodes, and rule 5 has REFERS_TO_ACT to `act:information-technology-act-2000`.

**SC-6 (approved). Admin metadata for rules (changes 3.4).** `issued_under` becomes `{act_id, sections: [string]}`, because the Jurisdiction Rules are issued under sections 34, 47 and 58 (05 Phase 2). It is stored as `Act.issued_under_section` (list). New optional key `prescribes_for: [{rule, section, note}]` creates the PRESCRIBES_FOR edges that 2.4 says come from admin metadata; each `rule` must exist in the parsed document and each `section` in the parent Act, or the job fails with PARSE_VALIDATION_FAILED. For the Jurisdiction Rules: `[{rule: "3", section: "34"}, {rule: "4", section: "47"}, {rule: "5", section: "58"}]`.

**SC-7 (not approved). OCR for legal ingestion.** Legal ingestion OCRs with `en` only, not OCR_LANGS: with `en,hi`, English text came back with Devanagari digits (D-4). OCR keeps line structure (`paragraph=False`, boxes grouped into lines by vertical position), so P-06, P-07 and P-13 can see line starts. Running heads of printed compilations (`82 CONSUMER PROTECTION (E-COMMERCE) RULES, 2020 [R. 4`, `[80]`) are removed with P-01.

**SC-8 (decided: option a). Source of the E-Commerce Rules.** The supplied scan OCRs badly enough to produce wrong citations:
- About 25 labels are lost: rule 3(1)(c), (f), (i) to (l); 4(2)(b) to (d); 4(7); 5(4); 6(4); 6(5)(d), (f), (h), (i); 7(1)(b) onward; 7(4); and others. A lost label merges that sub-rule into the previous one, so `Rule 6(3)` would carry the text of 6(4).
- The enabling clause reads `sub-clause (2g) of sub-section (1) of Section 101`, which looks like an OCR error.
- Rule headings end in `(1)`, `.`, `_` or `-` at random.
- The first footnote has lost its marker.

Options:
- **(a) Recommended.** The operator supplies a copy with a text layer, ideally consolidated with the G.S.R. 328(E) amendment of 17-5-2021, which this compilation already includes. The SC-5 parser then handles it like the Jurisdiction Rules and SC-7 is only a fallback.
- **(b)** Ingest the scan with rule-level units only. No sub-rule Clauses are created, each rule is split at sentence boundaries under the 2.3 retrieval-unit rule (`-p1`, `-p2`), and citations name the rule only (`Rule 6, Consumer Protection (E-Commerce) Rules, 2020`). Accurate but coarse.
- **(c)** Defer the E-Commerce Rules.

In every option the operator supplies `as_on_date`, because the compilation shows no currency date.

**SC-9 (approved 2026-11-20; applied to 02, 03, 04 (P-18 to P-21) and 05 (G12)). Amendment notifications.** Triggered by `data/legal/2021 May 17.pdf`, which is G.S.R. 328(E) of 17 May 2021, the Consumer Protection (E-Commerce) (Amendment) Rules, 2021. It is the amending notification, not a consolidated text, so D-6 (option A) cannot use it.

- New optional metadata key `amends: {act_id}` (3.4), with `kind: rule`. The notification becomes its own Act node (`cp-e-commerce-amendment-rules-2021`). Its rules are Sections stored for provenance but never retrieval units, so the new wording is not embedded twice.
- P-19 Substitution. In the amending rules, `in rule N, for sub-rule (M), the following sub-rule shall be substituted, namely:— “(M) …”` (and `for rule N, the following rule shall be substituted`) replaces the target Clause's (or Section's) text in the principal rules with the quoted text, label stripped. The Section text is rebuilt and the changed units are re-embedded, all in one transaction. Insertions, omissions and any other wording fail the job with PARSE_VALIDATION_FAILED, so nothing is applied half-understood.
- P-20 Record. Each substitution creates an AMENDS edge from the amending Act to the principal Section, with `effective_on` (from metadata, default `as_on_date`) and `previous_text`, and adds the note `Subs. by G.S.R. 328(E), dated 17-5-2021 (w.e.f. 17-5-2021)` to `Section.amendment_notes`. The principal Act's `as_on_date` moves to the amendment date when that is later. This changes P-18 for this case: a notification that has been ingested as an Act node can be the source of AMENDS.
- P-21 Re-application. When the principal rules are re-ingested, the substitutions stored on their amending Acts are re-applied in the same transaction, so a `--replace` re-ingest never reverts rule 4(1). Re-ingesting the amendment changes nothing (R-16).
- Acceptance test G12. `cl:cp-e-commerce-rules-2020:4:1` begins `where an e-commerce entity is a company incorporated` and contains `nodal officer`, and the 2020 wording is gone from it. Section 4 carries the note and an AMENDS edge with `effective_on` 2021-05-17 and the previous text. The principal Act's `as_on_date` is 2021-05-17. A `--replace` re-ingest of the principal rules keeps all of this.

Observation: the amendment's enabling text reads `sub-clause (zg) of sub-section (2) of section 101`, while the 2020 original reads `… of sub-section (1) …`. Both are stored as printed (P-04 spirit).

- **A-11 (2026-11-20, 2.3 retrieval units; Phase 2).** Clauses of a Section that is itself a unit are not units, so no text is embedded twice. A unit over 2,000 characters is split into parts, preferring proviso boundaries and then sentence boundaries. The whole Clause keeps its full text and is not embedded; this keeps the G2 definition count at 47. A Section over 2,000 characters with no subsection Clauses is split the same way (`sec:{act}:{n}-pN`). The `act_id` property on legal nodes holds the act slug (`cpa-2019`).

**SC-14 (approved 2026-11-20: option c, c1 and c2; applied to 05 Phase 4 and Phase 6 exits; (a) may be added later if a paid key becomes available). Groq free-tier limits against the Phase 4 and Phase 6 targets.** Measured from Groq's response headers on 2026-11-20, account limits for `openai/gpt-oss-120b`: 8,000 tokens per minute and 1,000 requests per day. The token budget refills continuously, about 133 tokens a second; it does not reset once a minute. `max_tokens` is not reserved in full: a call with `max_tokens` 4,000 took about 455 tokens off the budget, against about 124 for the same call with 50. The headers show no daily token limit, but there is one: **200,000 tokens per day** (see O-6; this sentence was wrong when SC-14 was written).

One CASE_AND_LEGAL query makes 3 calls (planner, issue statement, responder). With the R-11 context cap of 18,000 characters (about 4,500 tokens), the responder system prompt and an output cap of 1,800 tokens, a query uses about 7,000 tokens (estimate; to be measured once the prompts exist). Consequences:
- A single query with a full budget is not throttled. p95 ≤ 20 s (Phase 4) can hold for queries that are about a minute apart.
- Sustained throughput is about 1 query a minute (8,000 ÷ 7,000). A second query inside the same minute waits about 50 s for budget, so the 1.2 retries run past the 45 s budget and E-12 returns 504.
- The evaluation run (at least 30 questions, Phase 4) needs at least 30 × 7,000 ÷ 8,000 ≈ 26 minutes of token budget. If the questions run back to back, the p95 measures waiting on the rate limit, not the pipeline.
- The Phase 6 soak test (20 concurrent queries) needs about 140,000 tokens, which is about 17 minutes of budget. Most of the 20 queries return 504 or 502 by design (E-01, E-12). The exit criterion says only 'no 500 responses', so read literally it can still pass, but it then shows little about behaviour under load. Ingestion uses the same budget (extraction cap 4,000, SC-11), so the 'one concurrent ingestion' adds to the shortfall.
- 1,000 requests a day is about 330 queries, before ingestion uses any.

Options:
- **(a) Paid (Developer) tier.** No spec change. The limits come from the account, so the measurement above is re-run after upgrading (the same header check) and recorded here. Groq bills per token, so the cost of the evaluation and soak runs can be estimated from `trace.llm` once the prompts exist.
- **(b) Fewer or smaller LLM calls.** Spec changes, chosen individually: (b1) when `mode` is not `auto`, skip the planner and use the question as `search_query` (changes C3; saves about 600 tokens and one request); (b2) lower the R-11 responder context cap from 18,000 to 9,000 characters (about 2,250 tokens less; R-11 still drops the lowest-ranked item first); (b3) lower the responder output cap from 1,800 tokens (R-19). Together these bring a query to about 4,000 tokens, so about 2 queries a minute. They make the latency targets easier but do not make the soak test meaningful, and (b2) and (b3) may cost recall and answer quality.
- **(c) Relaxed targets for the free tier.** (c1) Phase 4 latency is measured per query with the token budget full: `run_eval.py` waits for the budget to refill between questions (from the rate-limit headers) and leaves the wait out of the latency, so p95 ≤ 20 s measures the pipeline. (c2) Phase 6 soak: 20 queries submitted at once; the exit criterion becomes 'no 500 responses, and every response is 200, 502 LLM_UPSTREAM_ERROR or 504 QUERY_TIMEOUT with the error envelope', with the 200 count recorded. No change to the 45 s budget (E-12).

Recommendation: (c1) and (c2) now, so Phase 4 can finish on the free tier with an honest measurement, plus (a) if a paid key becomes available, because only (a) makes the 20-query soak test show real throughput. (b) is not recommended as the main fix: it saves at most about 40 % of the tokens and trades away recall.

**O-1 probe (2026-11-20; observation only, nothing changed).** The Cypher 25 `SEARCH` clause was tested on Neo4j 2026.10.2 in throwaway databases. The probe scripts are outside the repo and only read the real database. Findings:
1. Vector syntax: `MATCH (c:CaseChunk) SEARCH c IN (VECTOR INDEX case_chunk_embedding FOR $query_vec WHERE c.case_id = $case_id AND c.user_id = $user_id LIMIT $k) SCORE AS score`. `$k` and the filter values are parameters (R-01). Scores equal `db.index.vector.queryNodes` scores to 4 decimals.
2. A filter inside `SEARCH` needs the filtered properties declared on the index: `CREATE VECTOR INDEX … ON (n.embedding) WITH [n.case_id, n.user_id] OPTIONS {…}`. With the 2.2 DDL, the query fails with `PropertyNotFound` (22ND3: 'not an additional property for vector search with filters'). A `WHERE` after `SEARCH` is a post-filter: it returned 1 of 5 rows, so it has the same problem as the procedure. Filter predicates must be property comparisons joined by AND, with no OR. That is enough for case_id and user_id.
3. Full-text: `SEARCH c IN (FULLTEXT INDEX case_text_ft FOR $lucene LIMIT $k)` works, but `WHERE cannot be used together with FULLTEXT INDEX`. Case full-text search therefore still needs over-fetch then filter (R-09) whether it uses `SEARCH` or the procedure.
4. 4.2 open item, full-text `limit`: `db.index.fulltext.queryNodes(…, {limit: n})` returns exactly n rows (3 → 3, 50 → 50; 527 without a limit). 4.2's assumption holds on this server.
5. Small test (527 chunks: real Legal KB texts copied as chunks into case A, 27 chunks; case B of another user, 250 chunks; case C, 250 chunks): both approaches returned the exact top k (k = 5 and 15) with no out-of-scope rows. R-09 needed 2 to 4 rounds for case A.
6. Scale test (25,275 chunks: case A 25, case C 250, and 100 other-user cases each holding a near-copy of every text): **the R-09 loop stops at fetch_k 800 and misses most of a small case.** Recall against an exact scan: case A k=5 R-09 6/30, SEARCH 30/30; case A k=15 R-09 6/90, SEARCH 90/90; case C k=15 R-09 56/90, SEARCH 90/90. SEARCH was also faster (mean 8 to 35 ms against 48 to 147 ms). This is a deliberate worst case (overlapping content across users, as in the Phase 4 isolation test), but it shows that R-09 can return too few rows for a small case once the store grows. Through E-05, that wrongly downgrades the query to LEGAL_ONLY.

Became SC-15 (approved). The original note: case vector search uses `SEARCH` with the in-index filter, the case vector index gains `WITH [n.case_id, n.user_id]` (2.2; requires dropping and rebuilding the index), R-09 stays for full-text only, and the minimum Neo4j version becomes the tested 2026.10.2. An alternative that needs no index change: score the case's own chunks exactly with `vector.similarity.cosine` over the `casechunk_scope` index. Untimed; cases hold at most 200 documents.

**SC-15 (approved 2026-11-20; applied to 00 (Store), 02 (2.2), 04 (R-09, 4.2) and 05 (Phase 0); replaces the O-1 decision for case vector search only). Case vector search with the SEARCH clause and an in-index scope filter.** Grounds: the O-1 probe above (finding 6). Changes:
- **2.2 DDL.** The case vector index declares the scope properties: `CREATE VECTOR INDEX case_chunk_embedding IF NOT EXISTS FOR (n:CaseChunk) ON (n.embedding) WITH [n.case_id, n.user_id] OPTIONS {indexConfig: {`vector.dimensions`: 768, `vector.similarity_function`: 'cosine'}}`. `scripts/init_neo4j.py` stays idempotent. Startup (1.2) and GET /health count the index as not ready unless it is ONLINE and declares both properties (exit code 2 at startup).
- **4.2 case vector query** (replaces the procedure call):

  ```cypher
  CYPHER 25
  MATCH (node:CaseChunk)
    SEARCH node IN (VECTOR INDEX case_chunk_embedding FOR $query_vec
                    WHERE node.case_id = $case_id AND node.user_id = $user_id

  RETURN node.id AS id, node.text AS text, node.doc_id AS doc_id,
  ```

  Every value is a parameter, and scope.py supplies `$case_id` and `$user_id` (R-01). `$k` is the 15 case candidates before rerank (4.2).

**Phase 4 assumptions (2026-11-20; checkpoint 2, for operator review).**
- **A-33 (1.4 C3, 3.4 mode, E-06).** The planner runs on every query, including when `mode` is not `auto` (SC-14 option b1 was not chosen). A mode other than `auto` fixes the intent (case_and_legal → CASE_AND_LEGAL, legal_only → LEGAL_ONLY, case_only → CASE_ONLY), and the model's intent is used only for `auto`. With no case_id, a case intent becomes LEGAL_ONLY. E-06: mode case_only with no ready document returns 409 before any model call. For other modes, a case intent becomes LEGAL_ONLY with the gaps note 'The case has no processed documents yet, so only the statutory text was searched.' (E-06 gives no wording), and `trace.downgraded` stays false (E-06 does not ask for it, unlike E-05). LEGAL_ONLY uses the planner's `search_query` as the issue statement.
- **A-34 (2.5 messages, MemorySaver).** Each turn appends the question and the answer's summary to `messages`. The planner and responder see the last 3 turns (6 messages, each cut to 500 characters) inside a `<<<CONVERSATION>>>` block, which R-06 treats as data. Every other AgentState field is reset at the start of a turn, so a provision or chunk retrieved in an earlier turn can never pass the verifier in a later one.
- **A-35 (3.5 provision_id, A-11).** A split part (`…-pN`) is cited as its whole Clause or Section. The reranker merges parts of one provision into a single item (text in part order, best part's score), so `provision_id` is always a Section or Clause id, and the evaluation set labels Sections and Clauses only. The excerpt comes from the merged text.
- **A-36 (R-20, extends A-29).** The responder sees case chunks as `C1…` and provisions as `P1…`, and the citation text sits beside each P label. Its reply names labels only, and the verifier maps them back to ids and drops any label it did not send (R-21). - **A-40 (2026-11-21, SC-16, SC-17; how the approved checks work).** Fact grounding compares lowercase alphanumeric tokens after removing commas between digits (18,499 → 18499). **Phase 5 decisions (operator, 2026-11-23; recommended options).**
- **A-44 (3.2 rate limits).** A custom ASGI middleware with an exact per-IP sliding window over 60 s, in memory, and no new dependency (`slowapi` stays unused in requirements.txt). The key is the client address in the ASGI scope; `X-Forwarded-For` is ignored because the service binds to loopback. Categories: `POST /v1/query` 30, `POST /v1/cases/{id}/documents` 10, everything else 120 (including `/health`). Over the limit: 429 RATE_LIMITED, envelope `details.retry_after_seconds` and a `Retry-After` header with the seconds until the oldest request leaves the window (rounded up).
- **A-9 kept.** Router-level 404 and 405 keep FastAPI's default body; 3.3 has no code for them.
- **A-45 (3.4 GET /v1/legal/provisions).** Only Section and Clause ids resolve. A split-part id (`…-pN`, A-11) returns 404 PROVISION_NOT_FOUND, because answers only ever cite Section and Clause ids (A-35). `parent` is the Section for a Clause and null for a Section. `definitions` lists the cached R-13 concepts whose name appears as a whole word in the provision text, each with its definition Clause id (`id`), so a client can fetch the definition through the same endpoint; the provision's own definition is left out.
